Yes. For **AI Estate**, I would explicitly separate the database into two logical layers:

1. **AI Asset / Estate Catalog** — relatively stable, continuously updated information about *what exists* and *how components are mapped*.
2. **AI Runtime / Usage Telemetry** — high-volume, append-heavy information about *what happened for every request*.

This separation is important because the characteristics are very different. The catalog needs strong relationships, versioning and governance; runtime data needs high write throughput, time-based partitioning and aggregation.

# 1. Core Domain Model

The most important concept is that an **AI Asset** is not the same thing as a runtime request.

For example:

```text
Application
   │
   └── Agent
         │
         ├── LLM
         │     └── OpenAI GPT-X
         │
         ├── Embedding
         │     └── text-embedding-X
         │
         ├── Reranker
         │     └── Cohere Rerank-X
         │
         ├── Tool
         │     └── Salesforce
         │
         ├── MCP Server
         │     └── Jira MCP
         │
         └── Vector DB
               └── Pinecone
```

Then runtime:

```text
Application
     │
     ▼
Request #12345
     │
     ├── Agent invocation
     │
     ├── LLM call
     │
     ├── Tool call
     │
     ├── Embedding call
     │
     ├── Vector search
     │
     ├── Reranker call
     │
     └── Final response
```

The **catalog tells you what the relationship is**.

The **runtime layer tells you that the relationship was actually used**.

# 9. Asset Relationships

This is **the heart of AI Estate**.

Don't hardcode relationships such as:

```text
agent → model
agent → tool
```

Instead create a generic relationship table.

```sql
CREATE TABLE asset_relationship (
    relationship_id UUID PRIMARY KEY,

    source_asset_id UUID NOT NULL REFERENCES asset(asset_id),
    target_asset_id UUID NOT NULL REFERENCES asset(asset_id),

    relationship_type VARCHAR(100) NOT NULL,

    environment_id UUID REFERENCES environment(environment_id),

    valid_from TIMESTAMP,
    valid_to   TIMESTAMP,

    metadata JSONB,

    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

Examples:

```text
Contract Agent
     │
     ├── USES ──────────► GPT-X
     │
     ├── USES ──────────► Embedding-X
     │
     ├── CALLS ─────────► Salesforce
     │
     └── USES ──────────► Contract MCP
```

This table allows the architecture to evolve without database changes.

# 10. Versioned Mapping

This is important.

Suppose today:

```text
Agent A → GPT-X
```

and next month:

```text
Agent A → GPT-Y
```

You don't want to lose the historical relationship.

Therefore:

```text
Agent A
│
├── GPT-X
│     valid: Jan → Jun
│
└── GPT-Y
      valid: Jun → present
```

The `valid_from` / `valid_to` fields allow you to reconstruct the estate at any point in time.

This becomes very powerful for questions like:

> What model was Application X using when this request happened?

# 26. Don't Store Everything in PostgreSQL

For the initial POC:

```text
                PostgreSQL
                    │
        ┌───────────┴───────────┐
        │                       │
    Catalog                  Runtime
    Metadata                 Events
```

is perfectly reasonable.

But at scale I'd evolve to:

```text
                    AI ESTATE
                       │
              ┌────────┴────────┐
              │                 │
         PostgreSQL          Kafka
              │                 │
         Catalog DB             │
              │                 ▼
              │            ClickHouse
              │                 │
              │          Runtime Analytics
              │
              ▼
         Graph / Search
       OpenSearch / Neo4j
```

I would **not introduce Neo4j immediately**. PostgreSQL's relationship tables can handle the initial dependency graph. Introduce a graph database only when multi-hop graph queries become a demonstrated bottleneck.

Similarly, keep raw prompts/responses out of the primary relational tables unless required. Store them separately, with references from `ai_span`:

```text
AI_SPAN
   │
   └── payload_ref
           │
           ▼
       Object Store
       / Blob Store
```

This is especially important for enterprise privacy, retention, and cost.

# 27. One Additional Table I'd Strongly Recommend: `asset_snapshot`

Because your first layer is **continuously maintaining current information**, you need to distinguish:

> Current state

from:

> Historical state.

For example, today:

```text
Agent A → GPT-X
```

tomorrow:

```text
Agent A → GPT-Y
```

Create:

```sql
CREATE TABLE asset_snapshot (
    snapshot_id     UUID PRIMARY KEY,

    asset_id        UUID NOT NULL REFERENCES asset(asset_id),

    version         BIGINT NOT NULL,

    snapshot_time   TIMESTAMP NOT NULL,

    status          VARCHAR(50),

    configuration   JSONB,

    metadata        JSONB
);
```

Now you have:

```text
Asset
 │
 ├── Snapshot v1
 │     └── GPT-X
 │
 ├── Snapshot v2
 │     └── GPT-Y
 │
 └── Snapshot v3
       └── GPT-Z
```

This is extremely useful for **AI Estate lifecycle management**.

I'd therefore start your POC with:

```text
                         ┌───────────────────┐
                         │    AI ESTATE UI   │
                         └─────────┬─────────┘
                                   │
                         ┌─────────▼─────────┐
                         │    Estate API     │
                         └─────────┬─────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              │                    │                    │
              ▼                    ▼                    ▼
       Asset Catalog         Runtime API          Governance
              │                    │                    │
              ▼                    ▼                    ▼
        PostgreSQL             Kafka/Events         Policy Engine
              │                    │
              │                    ▼
              │               ClickHouse
              │                    │
              └──────────┬─────────┘
                         │
                  ┌──────▼───────┐
                  │ AI ESTATE    │
                  │ KNOWLEDGE    │
                  │ GRAPH        │
                  └──────────────┘
```

### And the key architectural principle should be:

> **Catalog answers "What exists and how is it connected?"**
> **Telemetry answers "What happened, when, how often, and at what cost?"**
> **Governance answers "Is it allowed, compliant, secure, and properly owned?"**

That gives you a clean foundation for your **Discover → Observe → Govern** model without coupling the product to LangGraph, LangChain, OpenAI, Google ADK, MCP, or any single AI framework.

### The key idea

The **AI Estate Collector** should have two modes:

**Discovery mode**

> "Tell me what AI-related assets exist."

**Observation mode**

> "Tell me what those assets are actually doing."

# Collector Architecture

I would avoid making one giant collector.

Instead:

```text
ai-estate-collector
│
├── collectors/
│   ├── kubernetes/
│   ├── docker/
│   ├── git/
│   ├── github/
│   ├── gitlab/
│   ├── cloud/
│   ├── sbom/
│   ├── mcp/
│   └── gateway/
│
├── detectors/
│   ├── agent_detector
│   ├── llm_detector
│   ├── embedding_detector
│   ├── reranker_detector
│   ├── rag_detector
│   ├── tool_detector
│   └── framework_detector
│
├── observers/
│   ├── otel
│   ├── api_gateway
│   ├── service_mesh
│   └── network
│
├── normalizer/
│
├── relationship_engine/
│
└── publisher/
```

The **normalizer** is particularly important.

For example, collectors might discover:

```text
Kubernetes:
  env MODEL_NAME=gpt-x

Git:
  import openai

SBOM:
  openai==X.Y

Gateway:
  model=gpt-x
```

The normalizer turns all of this into one canonical asset:

```text
MODEL
----------------------------
Name: GPT-X
Provider: OpenAI
Type: LLM

Evidence:
  Kubernetes
  Git
  SBOM
  Gateway
```

# Evidence-based discovery

I'd introduce an important concept called **Asset Evidence**.

Instead of simply saying:

```text
Application A uses GPT-X
```

store:

```text
Application A
     │
     ▼
Uses GPT-X
     │
     ├── Evidence: Kubernetes ENV
     ├── Evidence: Git dependency
     ├── Evidence: Gateway request
     └── Evidence: OTel trace
```

Then assign a confidence:

```text
DISCOVERED
OBSERVED
VERIFIED
```

For example:

```text
GPT-X
│
├── Application A
│      └── VERIFIED
│
├── Application B
│      └── OBSERVED
│
└── Application C
       └── DISCOVERED
```

This prevents your platform from confusing **configuration with actual usage**.

# One thing I'd add to your DB design

With this Collector concept, add:

### `collector`

```sql
CREATE TABLE collector (
    collector_id       UUID PRIMARY KEY,
    tenant_id          UUID NOT NULL,
    name               VARCHAR(255) NOT NULL,

    collector_type     VARCHAR(100),
    version            VARCHAR(50),

    environment        VARCHAR(100),

    status             VARCHAR(50),

    last_heartbeat_at  TIMESTAMP,

    created_at         TIMESTAMP NOT NULL,
    updated_at         TIMESTAMP NOT NULL
);
```

And:

### `asset_evidence`

```sql
CREATE TABLE asset_evidence (
    evidence_id        UUID PRIMARY KEY,

    asset_id           UUID NOT NULL,

    collector_id       UUID REFERENCES collector(collector_id),

    evidence_type      VARCHAR(100),

    source             VARCHAR(255),

    source_identifier  VARCHAR(500),

    observed_at        TIMESTAMP NOT NULL,

    confidence          NUMERIC(5,4),

    evidence_data      JSONB
);
```

Now your architecture becomes:

```text
Collector
    │
    ▼
Evidence
    │
    ▼
Asset Resolution
    │
    ▼
AI Asset
    │
    ▼
Relationship
    │
    ▼
Runtime Usage
```

That's a very clean data lineage.

## I would also define the Collector's contract early

Something like:

```json
{
  "collectorId": "collector-123",
  "timestamp": "2026-09-18T10:00:00Z",
  "source": "kubernetes",
  "assets": [
    {
      "type": "MODEL",
      "name": "gpt-x",
      "provider": "openai",
      "application": "contract-analyzer",
      "environment": "production",
      "evidence": {
        "type": "environment_variable",
        "key": "MODEL_NAME"
      }
    }
  ]
}
```

Then your Collector becomes a **pluggable discovery/observation agent** rather than being tightly coupled to your database.
